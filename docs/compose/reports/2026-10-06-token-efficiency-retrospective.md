# 复盘：4 个会话的 Token 去向与流程改进

> 时间：2026-10-06 · 范围：`API端点页面展开收起功能失效`、`检查并修复 V2 知识库文档`、
> `Git分支V1与V2版本管理方案` 三个会话 + 顺带的 `梳理项目未完成任务清单`
> 目的：找出「省 token / 少犯错 / 少走弯路」的可执行改进，并当场落地
> 数据源：`~/.dsh/sessions/--opdev-SqlReport--/session-*/session.v4.jsonl.zstd` 里的**真实 `usage`**

## 一、结论摘要

1. **98.6% 的 token 花在「重发历史」，模型输出只占 0.58%。** 所以 token 效率 ≈ `步数 × 上下文规模`，
   跟「让模型少说话」几乎无关。
2. **一步塞进历史的东西，后面每一步都要重发一次。** 一次全库 `grep`（225 命中 / 43k 字符）
   在第 4 步发生，就被后面 143 步各重发一次 → **2.33M tokens，占该会话 9.7%**。
3. **长会话是二次成本。** 上下文单调增长，总量 ≈ 步数 × 末尾上下文 ÷ 2。
   4 个会话共 440 步，末尾上下文 161k–300k，合计 **69.7M tokens**。
4. **批处理能力早就具备但欠用**：会话 1 有 118/147 步只发了 1 个工具调用。
5. **面比这 4 个会话大得多**：本项目 **32 个会话累计 632,453,040 tokens**（`session_cost.py --all` 实测），
   本次复盘的 4 个（69.7M）只占 **11%**。
6. **`write`/`edit` 会把改动后全文回显进上下文**——大文件编辑一次可加 2 万 tokens，
   且同样被后续每步重发。
7. （自我批评）**本次复盘自己就跑了 108 步 / 14.4M tokens、82% 的步只发 1 个调用**
   （撰写时实测，会话未结束）——比它分析的 4 个会话里的 3 个都贵。这恰好证明 R3
   （超 60 步落盘交接）是最该先执行的一条：连知道规则的会话也会滑进长会话。

已落地：硬性约束 **#20**、知识库分卷 **10-token-budget.md**、自查工具
**`scripts/agent/session_cost.py`**、门禁 **`tests/test_doc_budget.py`**（含 RED-GREEN 自证）。

## 二、方法与数据源（可复现）

```bash
# 1) 会话原文（zstd 压缩的 JSONL；本机无 python zstandard，用 zstd CLI）
zstd -dc ~/.dsh/sessions/--opdev-SqlReport--/session-79094439-…/session.v4.jsonl.zstd > run-logs/xx.jsonl
# 2) 一行出报告（本次复盘产品化成的工具）
venv/bin/python scripts/agent/session_cost.py --session 79094439
```

- **真实用量在** `assistant/message.data.usage`（`inputTokens` / `cacheReadTokens` / `cacheWriteTokens`
  / `outputTokens` / `totalTokens`），每步一条，不需要估算。
- `data.stream`（流式回放产物，单会话可达 1.5M 字符）**不进模型上下文**，统计时已剔除；
  早期用「字符数」代理时它会把结论带偏（本轮踩过，记在下方「走过的弯路」）。
- 会话标题在 `~/.dsh/storages/session_projcache/sessions/<id>.json` 的 `record.rows.title.val`；
  `storages/usage_history.json` 只有按天聚合，**没有按会话用量**。
- 定义：`ctx(步) = input + cacheRead + cacheWrite`（该步请求的上下文规模）；
  `新增(步 i) = ctx(i+1) − ctx(i)`（该步往历史里塞了多少）；
  `重发成本(步 i) = 新增(步 i) × 剩余步数`。

### 本轮复盘自己走过的弯路（一并记录）

1. 先用「记录字符数」做成本代理，把 `data.stream`（流式回放，单会话 1.5M 字符）算了进去，

## 六、预期收益（估算，非实测）

以会话 1（147 步 / 24.0M tokens）为例：

| 手段 | 估算 | 依据 |
|------|------|------|
| 收窄 top-3 大返回（grep 计数 + head + read offset） | 省 ~4M（≈17%） | 三步合计 5.6M，按体积降到 1/5 计 |
| 独立调用同步发，步数 147 → ~110 | 省 ~40% | 成本 ≈ 步数 × 平均上下文，二次效应 |
| 超 60 步落盘交接、分 3 段做 | 省 40%–60% | 每段从 ~19k 上下文重新起步 |
| 大文件编辑放后段 + 批量 | 省 ~5% | 第 60 步 1.73M 重发成本 |

**组合后单会话有望从 24M 降到 8–12M（约 50%–65%）**，且不降低交付质量——
这些手段压的是「重复重发」，不是「验证强度」。注意：cacheRead 通常按更低价计费，
所以「token 数」不等于「金额」；但结构（谁在重发、重发多少次）是一致的。

## 七、给后续会话的操作清单（贴墙上）

1. 开工前 10 步是省钱关键：先 `grep -c` 计数，再 `head` 截断，再 `read offset/limit`。
2. 一步能发 2–4 个互不依赖的调用，就别一步一条。
3. 会话超过 60 步或上下文超过 120k tokens：写 `run-logs/handoff/<日期>-<主题>.md`，换新会话。
4. 大文件（`render.py`/`config.py`/`report.py`）的修改集中到会话后段、一次批量改完。
5. 收尾跑 `venv/bin/python scripts/agent/session_cost.py --last 1`，把超阈步数字写进简报。
