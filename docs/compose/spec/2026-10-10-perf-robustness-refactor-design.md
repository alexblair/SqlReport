## 1. 背景与目标

### 1.1 为什么需要这份设计

2026-10-10 做了一次全仓只读盘点（23,115 行核心代码 + 83 个测试文件），发现 **37 项**可改进点，分 P0/P1/P2 三级。用户决定**全部修复**，但要求先有分批计划与规格，避免长任务跨会话后上下文污染导致「整体任务迷失」。

这份设计解决的问题是：**把 37 项发现变成可独立验收、顺序安全、可跨会话恢复的批次**。

### 1.2 目标（可验收）

| 编号 | 目标 | 验收方式 |
|------|------|----------|
| G1 | 消除全部 9 项 P0（含 3 项用户可见缺陷、1 项数据安全、1 项最大性能损耗） | 每项有专属回归测试 |
| G2 | 消除 P1 中的健壮性缺陷（静默失败、无限期卡死、无超时） | 每项有专属回归测试 |
| G3 | 收回已发生的架构分叉（重复实现语义不一致） | 字节级快照断言 |
| G4 | 完成两处 god-module 的结构收敛（`render.py` / `config.py`） | 输出字节不变 + 全量绿 |
| G5 | 全程**不改变可观测行为** | 基线 3042 tests 全绿（见 §4.1） |

### 1.3 非目标

- 不改技术选型（仍为纯标准库 + 4 个 pip 依赖，禁 Django/Flask/React/Node，硬性 #5）。
- 不新增用户可见功能。
- 不引入新的外部服务依赖。
- 不重写双引擎存储策略（只收敛重复实现，不改语义）。

## 2. 盘点结论与证据等级

### 2.1 证据等级定义（本设计强制标注，防止把推测当事实）

| 等级 | 含义 | 允许的措辞 |
|------|------|-----------|
| **A** | 已运行复现（有命令与输出） | 「实测」「复现」 |
| **B** | 已静态复核（grep/read/AST 确认行号与代码事实） | 「证据」「确认」 |
| **C** | 结构性存在但**未能复现实际影响** | 「结构性」「未能复现」——**不得**当作已确认缺陷 |

### 2.2 关键证据（等级 A，本机实测）

```bash
# 配置库连接开销（真实 MySQL 127.0.0.1:3307）
db.get_config_db() 连接 + SELECT 1：中位 82.2 ms
db.get_audit_db()  连接 + COUNT  ：中位  0.6 ms

# 登录页占位符
server._render_login_page("用户名或密码错误") → 含未替换 "{next_field}" == True
```

### 2.3 已核实的「非问题」（写在此处，防止后续重复投入）

`auth` 的 session/限流全部在锁内 · 请求级用户名走 `threading.local` 无串号 · `branding`/`app_config` 有进程级缓存 · 会话字典不会无界增长 · **全仓无 `deepcopy`** · 筛选表达式**不在行循环内**编译 · 路由正则在 import 期编译 · **无 SQL 注入**（标识符全部模块内常量） · **配置库无连接泄漏**（全 `try/finally`） · HTTP 缓存头设计正确 · `result_transform` 已做过性能实验并回退单趟化（`:186-191`）。

### 2.4 一条等级 C 记录（诚实标注）

**Redis 单例竞态**：`redis_cache.py:402-412` 是**无锁** check-then-act，结构性未同步。但独立复核时**两次实测均只得到 1 个 manager 实例**（含放大 `connect()` 窗口后），**未能复现**子代理声称的「8 线程 → 3 实例」。故本设计将其列为 P1 尾部项，修复方式为加锁（~10 行，风险低），但**不声称已造成实际损害**。

## 3. 分批策略（本设计的核心）

### 3.1 分层的依据：模块耦合实测

盘点实测的模块依赖（`import` 图，含函数内 late import）：

```
扇入最大（改它影响面最大）:
  app_config.py       被 14 个模块依赖   ← 全局配置，最高风险
  db.py               被  9 个模块依赖   ← 兼容转发层
  query_executor.py   被  6 个模块依赖
  static_cache.py     被  6 个模块依赖
  render.py           被  5 个模块依赖
  redis_cache.py      被  5 个模块依赖
  report.py           被  5 个模块依赖
  audit_db.py         被  5 个模块依赖
  result_transform.py 被  4 个模块依赖
  config_db.py        被  4 个模块依赖
```

### 3.2 唯一的真循环依赖（决定批次顺序的硬约束）

**实测确认存在强连通分量：`config_db.py ↔ db.py ↔ query_executor.py`**

容忍机制是 **13 处函数内 late import**（`config_db.py:76/92/118/325`、`query_executor.py:181`、`config_db.py:751` …），其中 `config_db.py:325` 附近的注释明确说明它们存在是为了让测试能 `patch("db._get_engine")`。

> **这是冻结契约，不是偶然。** 任何批次**禁止**「把 late import 提为模块级」或「合并这三个模块」——会直接打断 9 个模块的 import 与大量测试的 patch 点。

### 3.3 顺序约束（避免「A 改完 B 的目标代码已变」）

用户明确提出此风险。本设计用**三条规则**消除：

**规则 R1 — 写者单点（Write-scope 互斥）**
同一批次内，**任何文件只允许一个批次拥有写权**。批次表（§5）中每批显式列出 `写域`；跨批若需改同一文件，则**必须串行**且后批依赖前批完成。

**规则 R2 — 热点后置（Hotspot-last）**
扇入 ≥5 的文件（`app_config` / `db` / `query_executor` / `static_cache` / `render` / `redis_cache` / `report` / `audit_db`）的结构性改动**一律排在缺陷修复之后**。理由：结构改动期间这些文件处于「移动中」，任何并行的缺陷修复都会产生冲突。

**规则 R3 — 契约先行（Contract-first）**
若某批要改**被 ≥2 个模块调用的函数签名**，必须先在**该批内第一步**把签名与调用点一次性改完并全量绿，不允许跨批留半个签名。

### 3.4 批次总览（9 批，P0 → P3）

| 批次 | 主题 | 写域（互斥） | 项数 | 依赖 |
|------|------|-------------|------|------|
| **B1** | P0 用户可见缺陷速修 | `render.py`, `report.py`, `config.py`, `server.py` | 4 | — |
| **B2** | P0 配置库连接复用（最大性能） | `config_db.py`, `auth.py`, `server.py` | 2 | B1 |
| **B3** | P0 安全（ZIP 路径穿越） | `export.py` | 1 | — |
| **B4** | P0 调度器保活与卡死 | `scheduler.py` | 2 | B2 |
| **B5** | P1 性能（N+1 / 变换 / 缓存） | `config_db.py`, `report.py`, `result_transform.py`, `render.py`, `config.py` | 5 | B2 |
| **B6** | P1 健壮性（静默失败 / 超时 / 自愈） | `redis_cache.py`, `server.py`, `static_cache.py`, `render.py` | 6 | B4 |
| **B7** | P1 语义收口与架构去重 | `config.py`, `render.py`, `export.py`, `report.py`, `result_transform.py` | 4 | B1, B5 |
| **B8** | P2 死代码与整批清理 | 多文件（低风险） | 11 | B7 |
| **B9** | P3 结构拆分（god-module） | 新增 `ui_assets.py` 等 | 2 | B8 |

**为什么 B1 在 B2 之前**：B1 改 `server.py`（登录页、f 前缀）。B2 也改 `server.py`（连接复用）。按 **R1** 二者必须串行，且 B1 是 1–5 行的确定性修复、先做可立即降低线上风险，故 B1 先。

**为什么 B2 是全局最大收益**：单点把认证态请求的 ~161ms 连接开销降到 ~1ms（见 §2.2）。**建议 B1+B2 最先做。**

**为什么 B9 最后**：按 **R2**，`render.py` 扇入 5 且 B1/B5/B6/B7/B8 都要改它；结构拆分必须在所有这些改动**冻结之后**，否则拆分基线会持续漂移。

### 3.5 依赖图（不可违反）

```
B1 ──► B2 ──┐
              │         │
B3 ────┐      ├──► B5 ──┐
       ├──► B6 ──┐      ├──► B7 ──► B8 ──► B9
```

**依赖最小性已机器校验**（2026-10-10）：逐条剔除依赖后重跑 R1，剔除 **3 条冗余依赖**，使 B1/B3/B4 可并行。保留的均为**语义必需**，不只是文件重叠：

- **B4→B2 删除**：实测 B2 只改 `server.py`+`auth.py`（见 plan B2 Files 段），**不触及 `scheduler.py`**。
- **B7→B1 删除**：B1 改 `config.py:350` 附近（f 前缀），B7 改 `config.py:205`（`_escape`），相距 **145 行**且不同函数。
- **B7→B5 保留（语义必需）**：`report.py:1302-1308` 的 `_transform_rows` 正是 B5 派生态缓存所调用的函数（实测确认），两者在 `report.py` 相距仅 22 行。
- **B6→B3 保留**：剔除后出现 B3↔B7、B3↔B8 冲突。

**R1 可满足性已机器校验**（2026-10-10）：对全部 9 批两两检查「写域交叠 且 在依赖图中互无先后」的冲突对，结果 **0 对**；依赖图拓扑排序无环，拓扑序 `B1 → B3 → B4 → B2 → B5 → B6 → B7 → B8 → B9`。

> 初版依赖图曾有 **7 对**此类冲突（如 B5↔B6 同时改 `render.py`、B6↔B7 同时改 `render.py`、B3↔B7 同时改 `export.py`），已按 R1 修正——这正是用户担心的「A 改完 B 的目标代码已变」风险，故本校验是**必须重跑**的门禁，不是一次性结论。
> 复现脚本见 plan 末尾「附录：R1 校验脚本」。

## 4. 全局约束（每批都适用）

### 4.1 回归基线（冻结）

**基线事实**（2026-10-10 实测）：`venv/bin/python -m unittest discover -s tests/ -t .` → **Ran 3042 tests, OK (skipped=4), 66.851s**。

每批收尾**必须**复现 `Ran ≥3042` 且 `OK`。`-t .` 不可省（硬性 #8，否则隔离失效并连生产 Redis）。

### 4.2 行为不变的定义（G5 的判定标准）

对 `render.py` / `config.py` / `report.py` 的任何改动，判定标准是**输出字节不变**：

- B1 的 3 项显式缺陷**例外**（它们本就是修可见错误，属用户已批准的良性变化）。
- B7 的分类树缩进统一**例外**（需用户在 §7 裁决基准）。

### 4.3 工程纪律（引用既有硬性，不重复展开）

硬性 #5（选型锁定）· #6（必须 `venv`）· #7（改代码必须同任务更新知识库）· #8（`discover -t .`）· #12（同一问题失败 2 次停下找根因）· #14（产物落 `run-logs/`）· #17（交互改动验收）· #18（codegraph-first）· #19（改完 `.py` 跑 `codegraph sync`）· #20（token 预算）· #21（AOCI 改前定向读 + 收尾一次 maintain）。

### 4.4 禁止事项（由 §3.2/§3.3 推出）

1. **禁止**把 `config_db.py`/`db.py`/`query_executor.py` 的 late import 提为模块级。
2. **禁止**合并这三个模块。
3. **禁止**跨批并行修改同一文件（R1）。
4. **禁止**在 B9 之前对 `render.py` 做搬移类重构（R2）。
5. **禁止**抬 `tests/test_doc_budget.py` 的任何上限（硬性 #20 明文）。

## 5. 批次规格

> 完整任务级拆解（含每步测试代码、命令、期望输出）见 plan。本节只定**范围、验收、风险**。

### B1 — P0 用户可见缺陷速修（4 项）

| 项 | 位置 | 问题 | 验收 |
|----|------|------|------|
| B1-1 | `server.py:86-89`（调用点 `:510`） | 登录失败页输出字面 `{next_field}`，且 `next` 回跳丢失 | 新测试断言输出**不含** `{next_field}` 且含正确 hidden input |
| B1-2 | `report.py:1827`, `report.py:1894` | 两处横幅缺 `f` 前缀 → 页面显示 `{_icon("alert")}` | 测试断言含 SVG 图标、不含字面 `{_icon` |
| B1-3 | `config.py:350` | 写操作警示条缺 `f` 前缀 | 同上 |
| B1-4 | `render.py:3853` + 7 个调用点 | HTML 转义被塞进 JS 字面量 → 名称含 `'`/`\` 时 `confirm()` 语法错、**确认框静默失效** | 测试断言生成 JS 可被 `new Function()` 编译；名称 `O'Brien` 场景 |

**风险**：B1-4 是唯一有设计成分的（需引入 `_js_str()`）。其余 3 项为字符级修复。
**写域**：`server.py`, `report.py`, `config.py`, `render.py`。

### B2 — P0 配置库连接复用（2 项，收益最大）

| 项 | 位置 | 问题 | 验收 |
|----|------|------|------|
| B2-1 | `server.py:393` → `config_db.py:107-121` → `query_executor.py:199` | 配置库为 MySQL 但**每请求新建连接、无池**，实测 82.2ms/次 | 测试断言同一请求内 `_connect_mysql_config` 只被调 1 次 |
| B2-2 | `auth.py:201-217` + `server.py:435` | 每认证请求额外一次 `get_config_db` + `REPLACE INTO`，实测 77.8ms | 测试断言节流后不每次落库；**滑动过期契约不变** |

**风险：高**。MySQL 连接**不可跨线程并发共享**；池化必须「借出/归还 + 探活 + 加锁」。`conn.close()` 语义必须保持（参照 `query_executor.py:314-330` 的 `_PooledConnection.close()=归还`）。
**写域**：`config_db.py`, `auth.py`, `server.py`。
**注意**：大量测试 `patch("db._connect_mysql_config")`，B2 不得破坏这些 patch 点（§3.2）。

### B3 — P0 安全：ZIP 路径穿越（1 项，独立）

| 项 | 位置 | 问题 | 验收 |
|----|------|------|------|
| B3-1 | `export.py:522` → `:344` | 报表名未经清洗进 `os.path.join` → 路径逃逸（CWE-22） | 测试断言含 `/`、`..`、绝对路径的名称不会写出 `tmpdir` |

**风险：中**。清洗会**改 ZIP 内条目名（用户可见字节）**，需用户在 §7 裁决。
**写域**：`export.py`。无前置依赖（可在 B1/B2 之前或并行执行），但**必须在 B6、B7 之前完成**——这两批的写域都包含 `export.py`（由 R1 写者单点规则推出，见 §3.5 依赖图）。

### B4 — P0 调度器（2 项）

| 项 | 位置 | 问题 | 验收 |
|----|------|------|------|
| B4-1 | `scheduler.py:622-662` | 保活每 tick 都跑；`_next_keepalive_at`(`:273`) 是**死字段**；重活在派发线程内同步跑；连接**无 try/finally** | 测试断言：连接异常时不泄漏；保活按独立节拍 |
| B4-2 | `scheduler.py:403`（`try:` 之外） | 取连接失败时 `_running` 去重集**永不释放** → 任务永久静默停摆 | 测试：让 `get_config_db` 抛异常，断言 `sid` 已从 `_running` 移除 |

**风险**：中低。B4-2 修复仅 5–8 行。
**写域**：`scheduler.py`。**依赖 B2**（B2 改连接获取方式，B4 在其上做防护）。

### B5 — P1 性能（5 项）

| 项 | 位置 | 收益 |
|----|------|------|
| B5-1 | `result_transform.py:358-375` | 筛选内循环合并为单条 alternation，**实测快 2.8~3.5 倍**（99.0ms→35.8ms / 100k 行） |
| B5-2 | `config.py:940-953` + `:652-676` | 配置页单请求 12 次查询 → 7 次 |
| B5-3 | `config.py:948` → `config_db.py:2406` | 侧栏徽标去掉 N+1（加 `count_schedules`） |
| B5-4 | `config_db.py:1611` | `get_reports_by_category` N+1 → 1 次查询 |
| B5-5 | `report.py:1253-1280` | 派生态缓存拆分（筛选/排序两级）；修正 FIFO 与 LRU 注释不符 |

**风险**：B5-1 低（**禁止**改成 `lower() in`——Unicode 语义有边界差异）；B5-5 中（派生态必须仍只挂 L1、不进序列化）。
**写域**：`config_db.py`, `report.py`, `result_transform.py`, `render.py`, `config.py`。

### B6 — P1 健壮性（6 项）

| 项 | 位置 | 问题 |
|----|------|------|
| B6-1 | `redis_cache.py:402-411` | Redis 启动期连不上 → **永久降级，只能重启** |
| B6-2 | `redis_cache.py:90/276-278/289` | 重建锁无 owner 校验 + setnx/expire 非原子 + TTL 30s 短于合法慢报表 |
| B6-3 | `query_executor.py:84/125` | `?`→`%s` 全局替换会改坏含 `?` 的 SQL 字面量（同文件 `:389+` 已有引号感知实现可复用） |
| B6-4 | `server.py:322` | HTTP 无 socket 超时 + 每连接一线程无上限（实测标准库默认 `timeout=None`） |
| B6-5 | `render.py:2287-2303` | 静态资产失败后**永久降级为每页内联 ~103KB**，且 `render.py` 全文无 `import logging` |
| B6-6 | `static_cache.py:38/243-253` | `_last_invalidated` **无锁**读写（该文件无 `import threading`） |

**风险**：B6-4 **中偏高** —— `timeout` 作用于整个请求 socket（含写），大导出可能在慢链路被截断，必须 L2 实测；B6-2 中（TTL 取值是语义决策）。
**写域**：`redis_cache.py`, `server.py`, `static_cache.py`, `render.py`, `query_executor.py`。

### B7 — P1 语义收口与架构去重（4 项）

## 6. 关于「单文件是否太大」的结论

用户问：第 4 个子代理超时，是否说明单文件太大？

**结论：子代理超时 ≠ 文件太大。** 证据：

| 组 | 文件 | 总行数 | 结果 |
|----|------|--------|------|
| 组1 | `render.py` + `config.py` | **9549** | 按时返回，15 项 |
| 组3 | `config_db.py` + `query_executor.py` + `redis_cache.py` + `static_cache.py` + `db.py` | 4079 | 按时返回，16 项 |
| 组2 | `report.py` + `result_transform.py` + `export.py` | 3425 | 按时返回，14 项 |
| **组4** | `server.py` + `auth.py` + `api_handler.py` + `scheduler.py` + `audit_db.py` 等 9 个 | **4822** | **超时** |

组 1 带的是**最大的两个文件**（9549 行）却按时返回；组 4 行数**并非最多**却超时。所以超时的成因是**该组文件数最多（9 个）**、跨文件取证（连接生命周期、线程模型、时序实测）成本高，**不是单文件体积**。

**但架构拆分依然值得做**，理由独立于超时：

1. **`render.py` 的 48% 是字符串字面量**（3129/6578 行 = 154,597 字符），其中 `_COMMON_CSS` 单块 1186 行。这让「读 render.py 改一个函数」的上下文成本约为同规模纯逻辑文件的两倍。
2. **`config.py` 的 36 个 `handle_*` 混合五层职责**（路由 + 表单解析 + 落库 + 审计 + HTML 渲染），单函数最长 242 行（`_report_form_html`，22 个参数）。
3. `render.py` 最长函数 **492 行**（`build_api_endpoint_form_html`）。

**保守建议**（已写入 B9）：只做**纯搬移**（常量外移 + 按实体分文件），**不做任何设计改动**，输出字节不变、全量测试可证。这样收益（上下文成本）明确、风险可控。

### 7.3 D3 案例与三方案对比

**现状代码**（`export.py:344-352`）：落盘名与 ZIP 条目名共用**同一个** `filename`，且该值来自报表名（`export.py:522`）。

> **残留说明（诚实标注）**：方案 C 下，若报表名含 `../`，则 ZIP **条目名**仍含 `../`——这是**解压方**的 zip-slip 面，不由本仓控制（本仓不是解压器）。本仓自身的漏洞（服务端自己写盘越界）已消除。若用户希望连条目名也清洗掉 `../`，那就是方案 A 的取舍。

## 7.5 D5 大白话解释

### D5-a 审计日志里的「IP 地址」可能记的是假的

**现状**：如果配置里开了 `trust_xff`（默认**关**），服务端会取 `X-Forwarded-For` 请求头的**第一个** IP 当成访客 IP。但这行头是客户端**可以自己随便写**的。

**大白话**：就像门卫记录访客姓名，但姓名是访客自己报的。买了代理的人可以把自己的 IP 写成任何值，审计日志里就留下假 IP。

**但**：`trust_xff` **默认是关的**（实测确认），关了就用真实 socket 对端 IP，没问题。所以这只在**你开了这个开关**时才是问题。

**若改成“取最右边的 IP”**：会改变**已经记录下来的 IP 值**——历史审计与新增审计的语义不一致，且要改现有测试。

**建议**：**跳过**。或者只做「IP 格式校验」（非法格式不入库），这不改正常值。

### D5-b Excel 打开导出的 CSV 时可能自动执行公式

**现状**：导出的 CSV 里，以 `=`、`+`、`-`、`@` 开头的单元格会被 Excel/WPS 当**公式**执行。

实测字节：
```
"a","b"
"=1+1","@SUM(A1)"     ← Excel 打开会真的算 1+1
```

**大白话**：如果某个报表里存了用户填的内容（比如备注字段），而那人填了 `=1+1`，你导出后双击用 Excel 打开，它就被当公式跑了。恶意写法甚至能让 Excel 去联网拉外部数据（叫 DDE）。

**但**：这要求「数据库里存了以 `=`/`+`/`-`/`@` 开头的文本」+「有人用 Excel 打开」。你们的报表数据是业务库里的，如果都是数字和正常中文，实际风险低。

**若中和**：会在这些值前面加一个 `'`，**字节会变**——用户如果拿 CSV 做程序处理（不是 Excel 打开），可能被这个 `'` 干扰。

**建议**：**跳过**，或做成配置开关（默认关）。不要默认开启。

### D5-c 一个网址参数就能让页面卡死（这个建议做）

**现状**：报表页的 `page_size` 参数**没有上限**（`report.py:2210-2217` 只保证 ≥1）。

**实测发现**：你们**35 张报表里有 34 张**的 `allow_all_output=1`，这正好**关闭了行数护栏**。

**大白话**：任何人把网址改成 `?page_size=1000000000`，服务器就会把这**整张表**一次性读进内存、拼成 HTML 发回去。表大的话服务器内存飙升、别人跟着卡。这不需要登录后台，只要有报表页的访问权。

**若封顶**（比如 1000）：一个本来习惯用大 `page_size` 一次看全表的用户，行为会变——这**是**行为变化。

**建议**：**做，但上限取值要高**（如 5000 或 10000，覆盖正常「一次看多点」的需求），并**在页面上明确提示被截断**，而不是静默改变。这是三项里唯一**建议实际做**的。
